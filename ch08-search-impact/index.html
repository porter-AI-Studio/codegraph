第 8 章 · Part 4：實戰應用與進階

搜尋與影響力分析實踐

掌握 MCP 工具的分流（1.x 預設只剩 codegraph_explore），並用真實的 trace、impact、affected 輸出，讓 Agent 以最少的調用完成代碼探索。

8.1 MCP 工具的智慧分流（0.9.x 的 10 個工具 → 1.x 預設 1 個）

ℹ️
1.x 起，MCP 預設只露出 codegraph_explore 一個工具

官方依實測的 Agent 行為，改成「一個強工具比一堆窄工具更不容易選錯」： codegraph_explore 一次呼叫就回傳相關符號的原始碼、符號之間的呼叫路徑與影響範圍摘要。 其餘工具（node、search、callers、callees、 impact、files、status）仍可使用，只是預設不列出， 因為它們回傳的內容已經內嵌在 explore 的輸出裡。 需要時用環境變數 CODEGRAPH_MCP_TOOLS 重新啟用（例如 explore,node,search,callers）， 或直接用對應的 CLI 指令。

以下是 0.9.x 時期的 10 個工具（其中 trace、context 不在官方 1.x README 的工具清單裡），設計上分為兩類： 重型工具在任務開始時一次給足完整結構； 輕型工具在精準修改階段提供外科手術式的點狀查詢。 請參考以下決策樹，針對不同開發場景選擇對應的查詢工具：

ℹ️
重型工具 vs 輕型工具的費用差異

重型工具（context、trace、explore）每次調用約返回 2,000～10,000 tokens 的結構化資料，但能取代 10～20 次 grep/read；輕型工具每次返回 <500 tokens，適合精確點狀查詢。實務上一個架構探索任務通常只需 1 次重型 + 2～3 次輕型工具調用。

💡
全部設為自動允許

這 10 個工具全部是唯讀查詢，不會修改任何原始碼或檔案。 建議在 .claude/settings.json 配置完整的自動允許清單， 省去每次調用時手動點擊確認的摩擦（詳見 8.5 節）。

8.2 調用鏈追蹤實戰：codegraph_trace（0.9.x）

codegraph_trace 是整個工具集中最高頻使用的「核心神技」。 它能回答「從 Controller 到 SQL 執行，中間經過了哪些方法？」這類問題， 並且能穿透 EventEmitter、回呼函數、React 重渲染等動態分發邊界—— 這是 grep 無法做到的。

bash 
# trace 是 MCP 工具，沒有同名的 CLI 指令；由 Agent 自動呼叫，也可以直接要求它：
請用 codegraph_trace 追蹤 merge_copy 如何走到 sanitize_copy

# 1.x 的 MCP 預設已不列出 trace（見下方說明）；CLI 沒有對應指令。
# 1.x 上最接近的做法是 explore：
codegraph explore "how does merge_copy reach sanitize_copy"

以下是在一個小型 Python 專案（6 個檔案、138 個節點）上，用 CodeGraph 0.9.6 的 MCP trace 工具 實測的真實輸出（函式本體為節省篇幅而省略）。每一跳都附上 檔案:行號，目的地函式接著呼叫了什麼也一併列出：

trace 輸出（0.9.6 MCP 工具，實測 2026-10-10） 
## Trace: merge_copy → sanitize_copy

Full execution path below — 2 hops, each with its body, plus what the destination calls. This is the complete flow; answer from it.

2 hops:

1. merge_copy (scripts/scaffold.py:103-121)
      103	def merge_copy(o, copy_path):
      ...（函式本體，此處省略）
      112	    c, errs = sanitize_copy(c, o)
      ...
   ↓ calls@112   c, errs = sanitize_copy(c, o)
2. sanitize_copy (scripts/scaffold.py:142-195)
      142	def sanitize_copy(c, o):
      ...（函式本體，此處省略）

### `sanitize_copy` then calls (the destination's immediate work):

- _str (scripts/scaffold.py:124-125)
- _dicts (scripts/scaffold.py:128-139)
⚠️
同名函式：trace 只會挑其中一個

這個專案裡有兩個 main（scaffold.py:397 與 gen_copy.py:198）。 要求「從 main 追到 sanitize_copy」時，trace 只回報其中一條路徑， 而且不會告訴你還有另一個同名起點：

從 main 出發（0.9.6）：只走了 gen_copy.py 的那條 
## Trace: main → sanitize_copy

3 hops:

1. main (scripts/gen_copy.py:198-243)
   ↓ calls@231   errs = validate(c, o)
2. validate (scripts/gen_copy.py:135-144)
   ↓ calls@140   clean, errs = sanitize_copy(c, o)
3. sanitize_copy (scripts/scaffold.py:142-195)
ℹ️
1.x 官方的工具清單裡沒有 codegraph_trace

官方 1.x README 的 MCP 章節只列出 codegraph_explore，以及可重新啟用的七個工具 （node、search、callers、callees、impact、files、status）， 其中沒有 trace；官方的說法是 explore 要能回答「X 如何走到 Y」這類流程問題，並附上符號之間的呼叫路徑。 我在 1.6.2 對同一個小專案問「how does merge_copy reach sanitize_copy」，CLI 的 explore 回的是 影響範圍（Blast radius）加相關原始碼，沒有像上面 trace 那樣逐跳列出的路徑。 路徑資訊在較大的專案或 MCP 模式下是否會出現，我沒有驗證，請在自己的專案上實際跑一次。

實務上（0.9.x 的 trace）請看輸出裡的 檔案:行號 確認是不是你要的那一個；同名符號改用唯一的名稱當起點 （例如上面的 merge_copy），路徑就不會模糊。

ℹ️
通常一次 Trace 就夠了

官方 7 個開源專案的基準測試中，有索引時 Agent 通常只要 1～4 次 codegraph_explore 就能回答架構問題並停止；沒有索引的對照組最多花到 43 次工具調用、19 次檔案讀取（詳見第 4 章）。

8.3 影響力分析實戰：codegraph_impact

在修改核心服務（如 UserService）之前， 影響力分析可以告訴你這個改動會波及哪些符號。以下同樣是 1.6.2 的實測輸出：

bash 
# 評估修改 sanitize_copy 會波及哪些符號
codegraph impact sanitize_copy

# 搭配 --depth 限制搜尋深度（避免影響半徑過大）
codegraph impact sanitize_copy --depth 3
impact 輸出（實測，2026-10-10） 
Impact of changing "sanitize_copy" — 9 affected symbols:

function sanitize_copy (python) — scripts/scaffold.py:142
scripts/scaffold.py
  function    sanitize_copy:142
  function    merge_copy:103
  function    main:397
  file        scaffold.py:1

scripts/gen_copy.py
  function    validate:135
  function    main:198
  file        gen_copy.py:1

tests/test_scaffold.py
  function    test_sanitize_rejects_non_dict:3
  file        test_scaffold.py:1

輸出依檔案分組，列出受影響的函式與檔案；測試函式（test_sanitize_rejects_non_dict） 也在清單裡，因為它直接呼叫了 sanitize_copy。 Agent 可以根據這份清單精準決定需要閱讀哪些程式碼。

impact 回答的是「哪些符號會被波及」，不是「該跑哪些測試」。 要直接取得測試檔清單，用的是 codegraph affected（它沿著 import 相依往外追，找出測試檔）：

bash 
# impact 回答「哪些符號會被波及」；要知道「該跑哪些測試」改用 affected
codegraph affected scripts/scaffold.py
affected 輸出（實測，1.6.2） 
Affected test files (1):

  tests/test_scaffold.py
ℹ️
同一份程式碼，0.9.6 找不到、1.6.2 找得到

在同一個專案上，0.9.6 的 affected 回報 No test files affected by the changed files.； 1.6.2 才找出 tests/test_scaffold.py。圖的邊數也從 297 條增加到 329 條。 如果你的 CI 靠 affected 挑測試，升級後的結果可能和以前不同，請重新驗證一次。

8.4 結合 Vitest 的增量測試工作流

影響力分析最強大的應用之一是與測試框架整合，實現增量測試： 只跑與本次 git 變更有直接關聯的測試，而非每次都執行完整測試套件。 在大型專案中，這可以將 CI 時間從數分鐘縮短到數十秒。

增量測試漏斗流程圖 (Incremental Test Pipeline)
1. Git Diff 檢測變更
找出所有修改過的原始碼檔案 (ex: UserService.ts)
▼
2. CodeGraph 影響力反推
codegraph affected：反向追蹤所有受波及的模組與測試檔
▼
3. 執行測試 (Vitest)
xargs vitest run：精準只跑 3 個相關測試，跳過其餘 1000 個
bash（增量測試 Pipeline） 
# 結合 codegraph affected 只跑有風險的測試
git diff --name-only HEAD | codegraph affected --stdin --quiet | xargs vitest run

這條指令的三個步驟：

  1. git diff --name-only HEAD：取得與上一個 commit 相比發生異動的檔案清單。
  2. codegraph affected --stdin --quiet：根據異動檔案，反向追蹤所有受影響的測試檔案。
  3. xargs vitest run：只執行這些有風險的測試，跳過其餘測試。

建議封裝為 package.json script，方便 CI 和本地開發者統一呼叫：

package.json 
{
  "scripts": {
    "test:affected": "git diff --name-only HEAD | codegraph affected --stdin --quiet | xargs vitest run",
    "test": "vitest run"
  }
}
⚠️
注意：首次執行前需確認 codegraph.db 已同步

codegraph affected 依賴本地知識圖譜的完整性。若剛完成 git pull 拉入大量變更，建議先執行 codegraph sync 確保圖譜已更新，再執行增量測試指令，否則可能漏掉新增符號的影響分析。

8.5 允許清單：消除 MCP 工具確認摩擦

預設情況下，Claude Code 每次呼叫 MCP 工具都需要手動點擊確認。 由於 CodeGraph 的工具全為唯讀，可以在 .claude/settings.json 加入允許清單。 下面是 0.9.x 時期逐一列出 10 個工具的寫法；1.x 的官方做法是只加一條萬用規則 mcp__codegraph__*，之後即使用 CODEGRAPH_MCP_TOOLS 重新啟用其他工具也已經被允許（第 6 章有範例）：

.claude/settings.json（0.9.x：逐一列出 10 個工具） 
{
  "permissions": {
    "allow": [
      "mcp__codegraph__codegraph_search",
      "mcp__codegraph__codegraph_callers",
      "mcp__codegraph__codegraph_callees",
      "mcp__codegraph__codegraph_impact",
      "mcp__codegraph__codegraph_node",
      "mcp__codegraph__codegraph_files",
      "mcp__codegraph__codegraph_status",
      "mcp__codegraph__codegraph_trace",
      "mcp__codegraph__codegraph_explore",
      "mcp__codegraph__codegraph_context"
    ]
  }
}
⚠️
僅適用於唯讀工具

這份清單只涵蓋 CodeGraph 的查詢工具。 會修改檔案的工具（Edit、Write 等） 不應加入自動允許，應保留人工確認的安全閥。

8.6 輕型工具速查

在精準定位符號、微調程式碼的階段，以下輕型工具是你最常用的工具箱。 查詢延遲通常在 1 ms 以內（SQLite FTS5 + 索引查詢）， 比傳統 grep 全文掃描快 100x 以上：

bash（輕型工具速查） 
# 快速定位符號所在的檔案與行數
codegraph query UserService

# 查詢直接調用者（上游）
codegraph callers UserService.authenticate

# 查詢直接被調用者（下游）
codegraph callees UserService.authenticate

# 取得單一符號的詳細資訊與源碼
codegraph node UserService.authenticate

# 比 OS 更快的結構化檔案樹導航
codegraph files "src/service/**"

# 確認目前索引狀態
codegraph status
💡
工具使用原則：重型先行，輕型收尾

（0.9.x 的做法；1.x 預設只露出 codegraph_explore，架構探索與確認範圍都從它開始，需要點狀查詢時再用 CODEGRAPH_MCP_TOOLS 啟用其他工具或改用 CLI。）架構探索初期用 codegraph_context 或 codegraph_trace 取得全局視圖；確認修改範圍時用 codegraph_impact；精準定位與讀取時用 codegraph_search / codegraph_node。遵循此分流策略，可讓每次對話的 Tool Call 次數維持在 3~5 次以內。
