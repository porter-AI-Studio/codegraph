CodeGraph 與同類工具比較

什麼情況用 CodeGraph、什麼情況該換別的，或是兩個一起用。

「程式碼知識圖譜」這個標籤底下，現在有不少工具。它們有的長得很像（都用 tree-sitter、都走 MCP），有的看起來像、其實要解決的是不同問題。 本章不打算幫你選出「最強」的一個，而是回答三件事：各家的定位差在哪裡、CodeGraph 在哪些情境站得住腳、哪些情境你應該換工具或搭配使用。

ℹ️
素材與時間點

本章整理自 2026 年 6～10 月的公開文章、各專案 README 與作者自己的實測筆記。星數、版本號、功能數量變動很快，凡是會變的數字，本章都標註「撰寫時（2026-10）素材所載」，或乾脆不寫。 各工具真正的最新狀態，請以官方 README 為準。

10.2 CodeGraph vs Graphify

這是素材裡被拿來比的最多的一對，兩篇比較文章（一篇偏實測心得、一篇偏介紹）的結論相當一致：它們不是直接競爭關係，只是都掛著「code knowledge graph」的標籤。

面向 CodeGraph Graphify
核心定位 agent 編輯程式碼時的導航加速器（常駐） 多模態、可分享的專案知識圖譜（偏一次性深度分析）
圖譜的角色 執行期查詢用的快取索引，不 review、不 commit 專案產物：可開啟、可 diff、可討論
保持新鮮的方式 檔案監控加 debounce 自動同步 手動更新或掛 git hook；--watch 只自動更新程式碼檔，文件與圖片要手動更新
涵蓋內容 只理解程式碼 程式碼加文件、schema、PDF、圖片等
資料外流面 較窄：只抽程式碼、存本機 SQLite、走本機 MCP 較寬：非程式碼外掛可能呼叫模型 API，需要自己審查設定
效能證據 官方有公開 benchmark，可重現 token 數字多來自第三方文章（例如 71.5 倍），其中一篇比較文的作者自己無法重現
安裝 npm 或 install.sh 安裝，再 codegraph install、codegraph init Python 生態：uv tool install graphifyy 後 graphify install

怎麼選

  • 選 CodeGraph：你的痛點是 agent 在編輯前花太多 tool call 做程式碼探索；你一個人或小團隊用，圖譜只當基礎設施；專案是中大型的純原始碼專案；想要自動同步，並希望資料外流面越窄越好。
  • 選 Graphify：專案橫跨程式碼、文件、SQL schema、架構圖；想要一份團隊能閱讀、討論、在 PR 裡 diff 的圖譜產物；要替新人做 onboarding。
  • 兩個都用：兩篇素材都提到互補用法，CodeGraph 常駐在 agent 的編碼迴圈裡，Graphify 在需要全貌時偶爾跑一次。代價是要維護兩份設定、兩個工具註冊。
  • 兩個都不用：原始碼少於 50 個檔案、寫一次性腳本，或問題根本出在需求不清、缺測試、沒驗證，圖譜幫不上忙（素材特別提醒這點）。

順帶一提，另一篇素材提到 Graphify 在撰寫時的星數比 CodeGraph 多，但星數反映的是話題熱度與傳播面向，並不等於對你的專案更適用，本章不拿它當選擇依據。

10.3 CodeGraph vs CBM：C 專案實測

網路上關於 CBM「實測超越 CodeGraph」的素材，大多不是中立來源。例如其中一支影片的作者自己改過 CBM，並請 Claude Code 當裁判打分數；另一類則是單一作者的搭配建議。所以我們另外做了一次有標準答案的實測，再來談結論。

實測設定

  • 對象：一個工業控制領域的 C／C++ 靜態專案（非公開專案，不揭露名稱與內容）。約 86 個檔案，其中 C 71 個、C++ 15 個，共約 1,052 個函式。
  • 標準答案：專案自己的事實抽取結果，其中 48 個函式卡片的呼叫者／被呼叫者已逐條對照原始碼核對。
  • 版本：codegraph 0.9.6 與 CBM（2026-10 版）。本書第 9 章以後談的是 1.x 新版，新版行為是否相同，需要你自己重跑確認。

結果

項目 CBM CodeGraph
簡單題（48 個函式卡片，共 137 條呼叫關係） 全中、0 誤報 全中、1 誤報
高扇入函式的呼叫者完整性（兩個函式） 漏 1 個、多列 2 個（另有誤歸屬與檔案節點混入）；漏列的原因是某個檔案的預處理解析失敗 分別 108／108、76／76，全數命中
同名辨識 可用「檔案＋起始行」鎖定唯一節點 CLI 只能用名稱查，類別、建構子、標頭檔的同名項目會混入（4 個誤報）
C++ new 建構子 有 CLI 的 callees 不列；官方資料有 instantiates 這種邊類型，實測中在資料庫內查得到（需自行查 DB，非 CLI 預設輸出）
執行緒／計時器入口 圖中有 CALL_REFERENCE 邊，可當入口候選 沒有對應的邊
48 張卡的查詢耗時 224 秒 68 秒
輸出量（token 近似） 約一半 約一倍（JSON 縮排加每列檔案與行）
函式指標間接呼叫、delete 隱含的解構 都沒有建邊 都沒有建邊
呼叫點行號 trace 輸出不給 CLI 輸出的行號是「定義行」；索引資料庫的邊有呼叫點行號，但要直接讀 DB 才拿得到

這份結果能說什麼、不能說什麼

實測後有一輪獨立複查，修正了幾個容易被誤讀的地方，請一併記住：

  • 48 張卡是簡單題；較難的樣本取自 CBM 一方的報告，有選樣偏差，不足以推論 CodeGraph 普遍比較準。
  • 耗時只代表這兩支測試腳本的工作流，不是兩個工具的絕對速度。
  • CALL_REFERENCE 邊找到的是「入口候選」，不是直接呼叫，也不能證明那個函式在執行期一定會被週期性地跑；每一條都要回頭核對原始碼。
  • 網路上流傳的「codegraph callers 會給呼叫點行號」並不正確，CLI 給的是定義行。
💡
結論：兩者互補，高風險分析建議交叉比對

CBM 在同名辨識與執行緒入口候選勝出，CodeGraph 在速度與呼叫者完整性勝出。兩者共同的盲區是函式指標間接呼叫與 delete 隱含解構，所以工具只能當「抓漏」的第二雙眼睛，標準答案仍要靠人與原始碼。 高風險的分析（例如要依據呼叫關係做刪除或重構決策）建議兩者交叉比對。

交叉比對流程示意 
# 高風險分析的交叉比對流程（概念示意）

1. 用人工整理的事實清單（facts）當主要依據
2. 用 CBM 以「檔案＋起始行」鎖定唯一節點，取呼叫者與被呼叫者
3. 用 CBM 的 CALL_REFERENCE 邊，取得執行緒／計時器入口「候選」
4. 用 CodeGraph 取呼叫者與被呼叫者（速度快、高扇入完整）
5. 以事實清單的檔案範圍過濾 CodeGraph 的同名誤報
6. 兩邊結果不同的邊 -> 回原始碼逐條核對，再決定補邊或排除

10.5 別只看廣告：token 數字的口徑

讀 CodeGraph 相關文章時，你會碰到 35%、57%、62%、70%、90%、94% 這些數字。它們看起來都在說「省 token」，其實量的東西、量的對象、量的人都不同。下表把素材中最常出現的幾組放在一起：

數字 素材所載的出處與口徑 要留意的點
62% tokens／44% 成本／88% tool calls／53% 更快 CodeGraph 官方 README，2026-08 重測：7 個開源專案、7 種語言、每組取 4 次的中位數，用 Claude Opus 4.8、對照組同樣封鎖 codegraph CLI 是「回答一個架構問題」的單題比較，不是整段開發工作的帳單；成本隨問題需要多少探索而差很大（57～78% 到接近持平）
35% 成本／70% tool calls／49% 更快 較早期的官方數字，被許多中文文章轉載 官方 README 自己說明：舊數字是在沒有封鎖 CLI 的測試環境下量的，對照組曾在 28 次中的 26 次偷偷用到 CodeGraph CLI，會使比較失真

99.2%／約 120 倍（CBM） CBM README：5 個結構查詢，對照逐檔 grep／read 探索 是特定微基準；論文跨 31 個專案的結果是約 10 倍少 token，且「品質分數」是 0.83 對 0.92，並非完全等價
71.5 倍（Graphify） 第三方文章：以某個知名開源專案加五篇論文與四張圖片為測試資料 比較文的作者表示無法重現；Graphify 自己的 README 沒有同風格的對照實驗
⚠️
不同工具的 benchmark 口徑不同，不能直接比大小

「62% tokens」、「99.2%」、「71.5 倍」分別是不同的題目、不同的對照組、不同的模型與不同的量測者。拿它們互相比較，就像拿 100 公尺跑的秒數去跟馬拉松的配速比。 尤其要警覺兩種情況：一是量測者同時是競品的作者；二是「官方數字」被轉載後混入了別的口徑。

至少三個口徑差異要分清楚

  1. 量的指標不同：token 處理量、tool call 次數、成本、速度、品質分數，是五種東西。省下 88% 的 tool call，不代表帳單少 88%。
  2. 量測者與利益關係不同：官方 benchmark（有公開方法、可重現）、單一作者在自己專案上的自測、競品作者維護的 leaderboard、頻道作者請 Claude 當裁判打分，可信度與適用範圍都不一樣。
  3. 測試題目不同：官方是「回答一個架構問題」；CBM 的 99.2% 是五個結構查詢；Graphify 的 71.5 倍混了論文與圖片。題目越偏向「大量探索」，省得越多，題目只要一兩步就能答完，差距就縮小，甚至持平。
  4. 吞吐與殘留不同：CodeGraph 官方 README 自己也承認，多輪對話結束時，它留在 context 裡的檢索內容比逐檔讀取的 agent 多約 80%（以 VS Code 為例是 67k 對 18k tokens）。處理的 token 變少，與 context 裡的常駐量變多，兩件事可以同時成立。

你自己能做的

最可靠的做法，是拿你自己的專案、你平常會問的問題，跑一次對照。以下是其中一篇比較文建議的評估方式，一個下午就能做完：

自己做一次對照 
# 在你自己的專案上，用同一個任務跑三次再比較
# 例：「照既有模式新增一個 API endpoint」

第 1 次：不裝任何圖譜工具（baseline）
第 2 次：只裝 CodeGraph（codegraph init 之後）
第 3 次：只裝候選工具（例如 Graphify 或 CBM）

# 每次記錄
- 第一次編輯之前的 tool call 次數
- 第一次編輯之前的檔案讀取次數
- 到第一次編輯為止的時間
- 改錯檔案的次數
- 漏掉的呼叫者／路由／相依（review 時才發現的）
- 索引過期造成的誤判次數

如果你的專案是少見的語言組合、或有大量巨集與函式指標（像 10.3 的 C 專案），更要相信自己的實測，而不是任何一篇文章。CBM 的論文也承認，巨集密集的 C 專案是它表現最差的類型之一，因為巨集不在 tree-sitter 的 AST 裡。

本章重點

  • CodeGraph 的強項是給 agent 的低摩擦、自動同步、單一工具；它不處理文件，也不是編譯器級解析。
  • Graphify、Understand-Anything 走「給人看的成品」路線；Serena 走「IDE 語意」路線；cognee 走通用記憶路線；CBM 與 code-review-graph 走與 CodeGraph 最接近、但各有側重的結構圖路線。
  • C 專案實測的結論是互補而非取代：CBM 在同名辨識與執行緒入口候選勝出，CodeGraph 在速度與呼叫者完整性勝出，高風險分析建議交叉比對。
  • token 節省數字的口徑差異很大，選工具前，用自己的專案跑一次對照。
