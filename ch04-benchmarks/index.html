第 4 章 · Part 2：核心功能與效能

效能基準測試與省代幣分析

用數據證實本地圖譜能為開發費用「減重」

一、 效能測試方法論

為了驗證 CodeGraph 的真實成效，作者採用了極為嚴謹的測試模型。測試環境採用 claude -p (以無介面 Headless 模式運行 Claude Opus 4.8)，對多個著名開源專案提出高度複雜的架構探索問題：

  • WITH 组 (啟用 CodeGraph)：啟用 CodeGraph 的 MCP 伺服器，同時 Agent 仍可自由選擇調用原生的 Read/Grep/Bash。
  • WITHOUT 组 (對照組)：停用 CodeGraph 的 MCP 設定，Agent 僅能依靠傳統的 find/grep/Read 進行代碼檢索。

每組均運行 4 次並取其中位數，以得出最貼近日常開發的統計學表現。

ℹ️
測試假設與資料詮釋

基準測試採用複雜的架構探索類問題（非簡單的讀檔任務），對 CodeGraph 效益最為明顯。對於只需讀取單一函數的簡單任務，Token 節省幅度會較低。所有數據為 4 次中位數，實際結果可能因問題複雜度和代碼庫結構而異。

「費用節省」低於「Token 減少」是正常現象：CodeGraph 的 MCP 工具查詢本身也會產生少量 Token，且部分成本是固定的系統提示。然而「工具調用減少」幾乎直接等比轉化為速度提升，因為每次工具呼叫都有網路延遲。

💡
為什麼費用的差距比其他欄位大得多？

費用取決於這個問題需要多少「探索」：對照組需要 28～43 次工具調用的專案（VS Code、Excalidraw、Tokio、Alamofire）， 費用省 57～78%；但 Django 只省 13%、Gin 幾乎持平，因為對照組在這兩個專案分別只用 14 次與 7 次調用就找到答案了。 也就是說：專案越大、問題越需要跨檔案追蹤，CodeGraph 越划算；小專案的簡單問題，差距就不明顯。

四、 邊際效益：項目規模與 Token 節省的關係

較早一輪的數據呈現「規模越大、節省越多」的趨勢（見下方圖表）。但官方 2026-08-05 的重新量測顯示， 節省幅度取決於「問題需要多少探索」，並不單純隨專案規模遞增： 較小的 Excalidraw（約 640 檔）Token 少 84%，比 VS Code（約 11k 檔）的 77% 還高； Gin（約 110 檔）Token 仍少 52%，但費用約持平。因此下面的圖表與敘述只代表較早一輪的結果，請當作趨勢參考，不要當成普遍規律。

（較早一輪數據）在小型專案（如 Gin，約 110 個檔案）中，由於程式結構簡單，Agent 僅靠原生 Grep 也能在較短時間內摸清脈絡，此時 Token 節省約為 23%。然而，一旦專案規模上升到萬個檔案的超大型代碼庫（如 VS Code），傳統 Agent 為了「尋路」而產生的上下文堆疊呈指數級膨脹，此時 CodeGraph 本地圖譜就能發揮極強的防迷路能力，將 Token 消耗直接降低 64%。

另外三個專案（Excalidraw 25%、OkHttp 54%、Alamofire 64%）因規模相近，已整合在第二節總表中。

五、 為什麼 CodeGraph 能帶來如此高的降幅？

  1. 拒絕大範圍掃查：啟用 CodeGraph 後，Agent 面對架構問題時通常只需要呼叫 1～4 次 codegraph_explore（官方 1.x 基準的說法；0.9.x 時期也會用到 codegraph_trace），即可透過本地索引精準解析出跨檔案的調用邏輯，完全省去了反覆 Grep 與遍歷檔案的上下文堆疊。
  2. 精確控制上下文大小：CodeGraph 回傳的是與問題相關的符號的逐字原始碼（依檔案分組）、符號之間的關聯，以及影響範圍摘要，而不是整個專案或整份檔案。模型不需要被動吞下大片無用的重複程式碼。
  3. 預防 Explore Agent 溢出：在沒有 CodeGraph 的情況下，Agent 時常會派生出大量的 Subagent 去並行 Grep，每個子代理都會攜帶大份上下文，這會導致費用隨運行時間呈指數型（Exponential）增長。
