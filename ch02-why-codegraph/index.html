為什麼 AI Agent 需要 CodeGraph

打破「重做尋路」的 Token 消耗黑洞

一、 森林中的尋路者：傳統 Agent 的探索痛點

在使用 Claude Code (cc) 或 Cursor 的 Agent 模式來修改一個陌生或龐大的專案時，你可能經常會看見以下的一幕：

當你提出一個高階架構問題（例如「請幫我查出用戶登入驗證的完整生命週期？」）時，Agent 為了找出跨文件的調用鏈，會立刻啟動一個 Subagent (子代理) 開始瘋狂調用工具： 

grep -r "login" src/
➔ 發現 120 處符合，嘗試列出檔案
➔ ls src/auth/
➔ 讀取 src/auth/service.ts 1-200 行
➔ 發現引用了 TokenValidator
➔ grep -r "TokenValidator" src/
➔ 讀取 src/auth/validator.ts ...
➔ (重複執行這個流程 20~50 次)

在這個循環中，Agent 可能一路累積數十次的 Tool Call 與大量 Token（官方量測中，沒有索引的對照組最多花到 43 次工具調用、19 次檔案讀取，耗時可達 2 分多鐘），僅僅是為了在它的「工作記憶（Working Memory）」中，拼湊出一張極其脆弱、離散的「代碼靜態結構圖」。

二、 工作記憶 vs 確定性結構

這種探索流程本質上是在使用極其昂貴的 LLM 推理運算，去反覆重新計算那些在本地早已確定、可被靜態分析推導出來的靜態結構資訊。這在軟體工程中是極大的浪費。

代碼與代碼之間的調用關係（如 A 函數在 line 40 調用了 B 函數，或 Class C 繼承了 Class D）是 100% 確定的。我們不應該要求 LLM 每次都在黑箱中用字串比對去「重新發掘」這些邊界。

CodeGraph 的核心思想：在本地一次性算好這張「關係網絡地圖」，以 SQLite 檔案格式落地儲存，並透過 MCP (Model Context Protocol) 將查詢工具直接掛載給 Agent。當 Agent 需要分析架構時，只需一次 API Query（如 1.x 的 codegraph_explore，0.9.x 時期為 codegraph_trace），就能精準拿到一條橫跨多個檔案的調用鏈。

三、 核心對決：Code RAG 不等於 Document RAG

許多人會問：我們為什麼不直接把整個代碼庫切片（Chunking）、算出向量值（Vector Embeddings）並存進向量資料庫中，讓 AI 透過語義搜尋就好了？

CodeGraph 的設計選擇很明確：它不使用向量檢索，索引完全來自語法樹（AST）與靜態結構，不需要向量資料庫或外部 LLM API。

這是因為代碼檢索與一般的文檔問答（Document RAG）有本質上的不同：

維度 Document RAG (文件問答) Code RAG (代碼探索)
底層依賴 語義相似度 (模糊統計) 語法樹與引用關係 (精確幾何)
容錯度 高 (大意相近即可) 極低 (符號對錯一個字即失效)
主導技術 Vector Embedding AST 解析 + 全文檢索 + 圖遍歷
典型問題 「本公司休假福利是什麼？」 「誰調用了 validateSessionToken？」

在代碼世界中，關係的精確性高於語義的相似度。如果僅使用向量檢索，當你搜尋 validateToken，向量庫可能會因為語義相近，把 checkAuth 或 verifyUser 也排在前面，卻唯獨漏掉了真正有硬性 Import 關係的變數名稱。

CodeGraph 證實了：在本地端，僅依靠 Tree-sitter 靜態解析出的調用圖 + SQLite FTS5 全文搜尋 + 經典圖遍歷算法 (DFS/BFS)，就能回答大部分「這個符號在哪裡、誰呼叫它、改它會影響誰」這類結構性問題（官方量測中 Agent 通常只需 1～4 次 explore 就能作答，見第 4 章），且成本極低、本地查詢速度可達毫秒級。1.x 的解析核心已改為原生 Rust kernel（第 1 章），原理仍是靜態解析加圖遍歷。

四、 何時需要 CodeGraph？（適用場景）

CodeGraph 並非所有情境的萬靈丹。了解它最適合（以及不太需要）的場景，能幫助你做出正確的工具選擇。

場景 是否需要 CodeGraph 說明
大型 Monorepo（10k+ 檔案） 強烈建議 ✓ 跨模組調用鏈複雜，Agent 探索成本極高
多人長期協作的既有專案 強烈建議 ✓ 歷史債、隱藏依賴多，符號關係圖讓 AI 快速定位
接手陌生 Codebase 強烈建議 ✓ 無需閱讀全部代碼，一次查詢即可理解架構脈絡
重構高耦合模組 建議 ✓ 精確找出所有 caller，防止漏改導致 runtime 錯誤
中型 API 服務（1k～3k 檔案） 可選用 有效但收益略低，視問題複雜度決定
小型個人腳本（<200 檔案） 不太需要 ✗ Agent 直接讀取全部檔案即可，建置圖譜成本不划算
一次性資料處理工具 不太需要 ✗ 生命週期短，無需建立持久性的符號索引
⚠️
建置成本說明

CodeGraph 需要在首次使用前對專案執行靜態分析並建立 SQLite 索引。在大型專案中這個過程可能需要數分鐘。但索引一旦建立完成，後續每次 Agent 查詢都是亞毫秒級回應，長期效益遠超初始成本。

💡
本章重點回顧

傳統 Agent 在大型代碼庫中陷入「重複探索 → 消耗海量 Token → 仍可能得到錯誤結果」的惡性循環，根本原因在於把「確定性的靜態結構問題」交給了「機率性的 LLM 推理」來解決。CodeGraph 的策略是：一次在本地算好符號關係圖（SQLite），透過 MCP 直接給 Agent 確定性的查詢工具，讓 AI 從「盲目搜索」進化為「精準導航」。對比向量 RAG，CodeGraph 選擇以 Tree-sitter AST + 圖遍歷取代語義相似度，因為代碼的世界需要的是精確性而非模糊匹配。

在下一章中，我們將介紹 CodeGraph 是如何利用其 MCP 工具（0.9.x 時期為 10 個，1.x 預設收斂為 codegraph_explore 一個）對 AI 進行「智慧分流」，主動引導 Agent 減少直接閱讀檔案，進而達到極佳的省 Token 與省時間成效。
